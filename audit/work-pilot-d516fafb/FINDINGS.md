## 1. [medium] Builder: 'latest frozen version within REVISION_DAYS' is read at build time, so the root depends on WHEN the window is built; late credit is missed and two operators get different roots

`pilot/build-tally.mjs:204`

Commit 953d7c7 takes the LAST leaf found for the job in the receipts of day-1..day+REVISION_DAYS. receipt(d) (line 137) returns null when WorkRegistry.latest(dayJobId(d)) is zero, and the loop treats null exactly like 'the job was not revised that day'. A day not anchored YET is therefore indistinguishable from a day with nothing, and nothing in the builder requires the window's last answer day + REVISION_DAYS to be anchored: the only time rule is toBlock < head (line 63). So the result depends on the wall-clock time of the run. (1) A build made soon after the window ends (the normal case) reads the ORIGINAL credit of every request answered in the last ~REVISION_DAYS; a revision anchored later (the split-panel late credit this commit exists for) is never paid, because the request is counted only in the window holding its Completed block and the window is consumed once posted (retire does not hand it back). A revision that removes an agent is the reverse: that agent was paid under a superseded version. No double payment across epochs. (2) Determinism fails: a governor rebuilding one or two days later reads more receipts and gets a different root, so the 24 h veto cannot tell an honest early build from a wrong root, and the README's 'rebuildable by anyone' property does not hold. (3) The refusal/success outcome is itself time dependent: a first frozen version with an empty oracleAcceptance refuses ('do not all answer this request'), and a superseded document can disappear from the records API, in which case frozenDoc throws an uncaught error (exit 1, not the documented exit 2). Live evidence (2026-10-29, Tenderly RPC): WorkRegistry.latest for 2026-10-26..28 is anchored and for 2026-10-29 is 0x00..00, so a build today of a window ending yesterday reads days 10-29..10-31 as empty. Job 569e4f4c-dc58-4e3f-9c9e-bc09837092a8 (oracle request d73223d0-54b9-4b91-a727-576597042689, attestedAt 2026-10-14T00:43Z, status attested) is listed in the 2026-10-13 receipt (0x7514...7b9a) with documentHash 9559ecc8...85fc, which api.imd.fun/work-records now answers 404 'unknown_record', and in the 2026-10-14 receipt (0xf35c...cff3) with documentHash 1c3fb8d5...9f96 naming agents 51553, 52713, 51046. A build between the Completed on 10-14 and the anchoring of the 10-14 receipt crashes on the 10-13 version (work record not found); a build afterwards pays three agents. Four specialists reported this (permissions, math, economics, flow); merged. Fix (builder only): before stage 3 refuse (exit 2) unless the receipt for addDays(day, REVISION_DAYS) is anchored for every credited request (or the run is past that day plus the plane's anchoring lag), treat a zero anchor for a past day as 'not proven yet'; write every receipt hash read, the head block and REVISION_DAYS into requests.json/tally.json; document in the README that an epoch's --to must be at least REVISION_DAYS + 1 days old.

## 4. [low] Builder lets a window end one block below an unfinalized head; a reorg after the log read can pay a Completed event twice across two epochs or never, and contiguity makes it uncorrectable

`pilot/build-tally.mjs:63`

Question 5 answered: an honest poster can always post (block.number only grows, so any toBlock < head at build time satisfies toBlock < block.number at inclusion; verified propose accepts block.number - 1 and refuses block.number). The defect is the other direction: head is getBlockNumber() ('latest'), logs are read at 'latest', and nothing requires toBlock to be finalized. The two-provider agreement check catches a lagging provider, not a reorg that happens after both answered. Mainnet still sees occasional 1-2 block reorgs. If a Completed event in block toBlock is reorged out and re-included at toBlock+1 or later, epoch N (built before the reorg) pays it and epoch N+1 (window starting at toBlock+1, `seen` is per run) pays it again; if an event is reorged INTO the window after the read, neither epoch pays it. The posted root is accepted regardless and the window cannot be recounted after 24 h. Anchoring lag of the daily receipts makes this rare but does not prevent it (a request answered just before midnight UTC whose receipt is anchored quickly). Four specialists reported it; merged. Fix: bound --to by the finalized block (client.getBlock({ blockTag: 'finalized' }) from both providers) and record toBlock's block hash in tally.json so a rebuild detects a reorg; optionally require toBlock + FINALITY_DEPTH < block.number in propose().

**Reproduction:**

Head H. Completed(R, 0, .., '/oracle/requests/U') is in block H-1 in both providers' view. node build-tally.mjs --pilot P --to H-1: accepted (H-1 < H); U credited in epoch N; the poster posts at block > H (accepted, H-1 < block.number). Block H-1 is reorged and the Intake completion lands in block H+1. Next build: nextFromBlock = H, window H..H+k contains Completed(R) at H+1, `seen` is empty, U credited again. Expected: each Completed counted once. Actual: U's agents receive 1.5 imdUSD twice (or, if the event moved into the window after the read, never).
